Engine ideas and primary sources

  • Stockfish: moves and generation

    Target masks, caller-provided output, generation specialization and optional SIMD emission inspire narrow generation changes. Its chess pin/check and fixed capacities do not transfer directly.

  • Stockfish: compact Move

    The chess move uses 16 bits. Taikyoku needs 11 bits per square and route identity; our safe complete-move prototype uses 64 bits.

  • Stockfish: state and attacks

    Incremental state, reversible per-move information and target-oriented attack queries are useful patterns. This repo already implements much of that structure.

  • Stockfish: architecture-specific slider techniques

    Contemporary source contains multiple slider techniques rather than one universal magic implementation. Per-line arithmetic is the more plausible adaptation to 36x36.

  • YaneuraOu: generation modes

    Target bitboards, caller output and specialized generation modes are applicable ideas. Modes that omit promotion choices cannot replace an all-legal-moves API.

  • YaneuraOu: Move16 and Move32

    Separate compact internal moves from richer execution metadata. Its no-op/null sentinels are unsafe to copy when real capture-and-return moves exist.

  • YaneuraOu: state and board groups

    Caller-owned StateInfo, distinct checked/trusted move contracts, selected movement groups and packed interchange offer design ideas without importing standard-shogi rules.

  • YaneuraOu: multiword bitboards

    Its two-word 81-square representation illustrates adapting bitboard width to a board. Our board requires 21 u64 words; line-local masks avoid scanning all 21 for simple rays.

  • Fairy-Stockfish: generalized riders and leapers

    Shared rider/leaper classes and variant masks suggest compiling by movement signature. Dense tables still become large for 303 types and 1296 squares.

  • Arasan programmer guide

    Its square array plus bitboards, 64-bit move records and saved reversible state show that hybrid layouts and richer compact moves are viable alternatives to a single representation.

  • Rust type-layout reference

    Actual sizes were measured with rustc 1.92.0 rather than assumed. Rust layout is not a stable serialization format; packed/niche representations need explicit safe conversion.
